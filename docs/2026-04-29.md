# 2026-04-29 작업 정리

## 개요
어제(04-28) 정리한 종베 인프라가 실제 쿼리 시 두 가지 운영 문제로 막혀 있었다.
오늘은 이 두 문제를 해결하고 실제로 종가배팅 후보가 대시보드에서 응답되는 데까지 도달했다.

1. **네이버 검색 API 401 (errorCode 024)** — 키 권한·동기화 이슈
2. **하위 에이전트 Anthropic API 429 rate limit** — Sonnet 토큰 한도 초과
3. **클라이언트 폴링 타임아웃 120s** — Supervisor 풀 파이프라인보다 짧아 빈 응답으로 종료

## 1. 네이버 검색 API 401 해결

### 증상
`/v1/search/news.json` 호출 시 모든 시도에서 401 반환.

```json
{"errorMessage":"Scope Status Invalid : Authentication failed.", "errorCode":"024"}
```

### 진단
- `.env`의 `NAVER_CLIENT_ID/SECRET` 자체는 정상 형식 (ID 20자, Secret 10자)
- 공백·따옴표·BOM 없음
- 직접 curl로 호출해도 401 동일

### 오해 단서
- 사용자가 보여준 "검색API 41ms" 로그는 **실패한 401 호출이 그대로 남은 것**
- 네이버 전체 서비스 상태 페이지는 사용자별 권한과 무관 (전 사용자 공통)

### 결국
사용자가 네이버 개발자센터에서 본인 앱의 사용 API 에 검색을 추가/저장하고 키를 새로 발급받음.
재테스트 시 `HTTP 200` + 4,246,520건 결과 확인.

```python
# httpx GET https://openapi.naver.com/v1/search/news.json
status: 200
총 4246520건 (표시 3건):
  · 삼성전자, 대형 3D 디스플레이 '에비에이션 라이더…' 32형 출시
  · 정 CEO, AI동맹 광폭 행보 4대그룹 총수와 회동
  · "패널 OLED 단가경쟁, 2029년 아부터 적자 폭 확대 예상"
```

### 추가 시도 — npm 기반 `@isnow890/naver-search-mcp`
- stdio 전용 패키지 (HTTP 모드 없음) → 우리 시스템(streamable-http)과 직접 호환 안 됨
- stdio→HTTP 프록시가 필요해서 통합 보류
- 우리 자체 `naver-news-mcp`(8050)가 정상 동작하므로 그대로 사용

## 2. 하위 에이전트 Haiku 다운그레이드

### 문제
종가배팅 쿼리는 **유니버스 20종목 × (OHLCV 90봉 + 뉴스 + 공시 + 외인기관)** 으로 컨텍스트가 매우 큼.
모든 에이전트가 `claude-sonnet-4-6` 사용 중이어서 분당 30K input tokens 한도 초과 → 429 반복.

```
anthropic.RateLimitError: Error code: 429
This request would exceed your organization's rate limit
of 30,000 input tokens per minute (model: claude-sonnet-4-6)
```

DataCollector도 429, Supervisor도 429 → 같은 큐레이트 결과: 빈 응답.

### 조치 — `src/claude_agents/base/claude_executor.py:24`
```python
# Before
DEFAULT_MODEL = "claude-sonnet-4-6"

# After
DEFAULT_MODEL = "claude-haiku-4-5-20251001"
```

### 적용 범위
- DataCollector / Analysis / Trading 모두 Haiku 사용 (모두 `BaseClaudeAgentExecutor` 상속)
- Supervisor 만 Sonnet 유지 (`supervisor/executor.py:27` 그대로) — 오케스트레이션 결정의 품질이 시스템 전체를 좌우하므로

### 결과
재시도 시 429 0회 발생. Analysis 단계에서 5,888자 풍부한 답변 생성.

## 3. 클라이언트 폴링 타임아웃 연장 (120s → 600s)

### 문제
`A2AMessageEngine._wait_for_task_completion(max_wait=120)` 기본값이 너무 짧음.
종가배팅 워크플로우는 4분 이상 소요 (Supervisor → DataCollector → Analysis 직렬).
대시보드의 `text_client.send` 가 120초에서 폴링 종료 → `merged_text=""` 로 반환 → state=completed/answer="" 표시.

이 동안에도 Supervisor 백엔드는 계속 작업해서 정답을 만들지만, 이미 클라이언트는 응답을 못 받은 상태.

### 조치 — `src/a2a_integration/a2a_lg_client_utils_v2.py:472`
```python
# Before
completed_task = await self._wait_for_task_completion(task_id)

# After
completed_task = await self._wait_for_task_completion(task_id, max_wait=600)
```

`_wait_for_task_completion` 시그니처는 그대로 두고 호출부에서 600s 명시.
다른 호출자에 영향 없음 (단일 호출 지점).

### 결과
대시보드 폴링이 570초까지 `working` 유지하다가 **completed** 로 정상 전환.

## 8. 회고

오늘의 두 번의 막힘은 **외부 API 권한**과 **클라이언트 측 시간 한도**라는 매우 다른 종류였다.
공통점은 둘 다 코드 자체는 옳았다는 것 — `closing_bet_mcp` 와 `dashboard.py` 는 어제 이미 옳게 짜여 있었고,
오늘 한 일은 운영 파라미터를 현실에 맞게 푼 것뿐이다.

다만 **Haiku 다운그레이드는 단순 토큰 회피가 아니라 의도된 역할 분리**다.
하위 에이전트는 도구 호출 오케스트레이션이 주 업무라 Sonnet의 추론 깊이가 거의 안 쓰임.
같은 사례는 다른 멀티에이전트 시스템에서도 흔히 등장하므로, 향후 모델 선택 가이드로 이 문서를 참조 가능.
